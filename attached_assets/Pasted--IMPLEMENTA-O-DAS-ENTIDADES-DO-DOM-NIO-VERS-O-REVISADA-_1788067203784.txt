# IMPLEMENTAÇÃO DAS ENTIDADES DO DOMÍNIO — VERSÃO REVISADA

Implemente no backend Spring Boot existente as entidades principais do domínio da aplicação.

O projeto já possui:

* Java;
* Spring Boot;
* Spring Data JPA;
* PostgreSQL;
* Flyway;
* Bean Validation;
* arquitetura MVC modularizada.

Mantenha a arquitetura existente.

Não recrie o projeto.

Não altere configurações existentes sem necessidade.

O objetivo desta etapa é implementar:

* entidades;
* relacionamentos;
* enums;
* repositories;
* migrations Flyway;
* DTOs;
* mappers;
* services básicos;
* exclusão lógica.

---

# 1. REGRAS GLOBAIS DE TODAS AS ENTIDADES

Estas regras são obrigatórias para TODAS as entidades.

## 1.1 Identificador

Todas as entidades devem possuir:

```text
id: UUID
```

O `id` é obrigatório.

No PostgreSQL utilizar tipo:

```text
uuid
```

---

# 1.2 DATA DE CRIAÇÃO

Todas as entidades devem possuir:

```text
criadoEm: Instant
```

Este campo é obrigatório.

Deve ser preenchido automaticamente na criação.

No banco:

```text
criado_em NOT NULL
```

---

# 1.3 DATA DE ATUALIZAÇÃO

Todas as entidades devem possuir:

```text
atualizadoEm: Instant
```

Esse campo NÃO é obrigatório.

Pode ser preenchido automaticamente quando ocorrer atualização.

---

# 1.4 DELETE LÓGICO

Nenhuma entidade deverá ser removida fisicamente pelas operações normais da aplicação.

TODAS as entidades devem possuir:

```text
ativo: Boolean
excluidoEm: Instant
```

A exclusão lógica deverá funcionar alterando:

```text
ativo = false
excluidoEm = instante atual
```

Não executar:

```sql
DELETE FROM ...
```

para exclusões realizadas através das regras normais da aplicação.

O registro deve permanecer no PostgreSQL para:

* histórico;
* auditoria;
* rastreabilidade;
* integridade de relacionamentos.

Ao criar uma entidade, a aplicação pode inicializar:

```text
ativo = true
```

Porém, seguindo a regra geral do domínio, a coluna NÃO deve possuir `NOT NULL`.

---

# 1.5 CAMPOS OBRIGATÓRIOS

Regra extremamente importante:

Somente são obrigatórios:

```text
id
criado_em
```

Todos os demais atributos devem aceitar `NULL`.

Isso inclui:

* Strings;
* enums;
* datas;
* números;
* booleans;
* Foreign Keys;
* descrições;
* relacionamentos.

Portanto NÃO criar `NOT NULL` em nenhum outro campo.

Não adicionar validações como:

```java
@NotNull
@NotBlank
```

nos DTOs apenas porque determinado campo parece conceitualmente importante.

As regras de obrigatoriedade serão definidas posteriormente de acordo com cada fluxo funcional.

---

# 1.6 RELACIONAMENTOS

Mesmo quando existir relacionamento entre entidades, as Foreign Keys devem ser inicialmente opcionais.

Exemplo:

```text
usuario_id UUID NULL
coruja_id UUID NULL
sessao_estudo_id UUID NULL
```

Criar Foreign Key quando houver relacionamento estrutural, porém permitindo `NULL`.

# 21. FLUXO CONCEITUAL DA RECOMPENSA

A arquitetura deve permitir futuramente o seguinte fluxo:

```text
Usuário conclui sessão
        ↓
SessaoEstudo
        ↓
OvoUsuario é validado
        ↓
Coruja é selecionada
        ↓
Recompensa é registrada
        ↓
CorujaUsuario é criada
        ↓
Coruja passa a aparecer no Viveiro
```

Ou seja:

```text
RECOMPENSA
```

é o registro de que algo foi concedido.

Enquanto:

```text
CORUJA_USUARIO
```

representa a posse atual da coruja.

Não misturar os dois conceitos.

# 30. PADRÃO DE SOFT DELETE NO BACKEND

Criar uma solução padronizada e simples para exclusão lógica.

Exemplo conceitual:

```java
public void excluir(UUID id) {
    Entidade entidade = repository.findById(id)
        .orElseThrow(...);

    entidade.setAtivo(false);
    entidade.setExcluidoEm(Instant.now());

    repository.save(entidade);
}
```

Não utilizar:

```java
repository.delete(...)
repository.deleteById(...)
```

nas operações normais da aplicação.

# 32. ENTIDADE BASE

Como TODAS as entidades possuem os mesmos campos:

```text
id
ativo
criadoEm
atualizadoEm
excluidoEm
```

é permitido criar uma entidade base simples.

Exemplo conceitual:

```java
@MappedSuperclass
public abstract class BaseEntity {

    private UUID id;

    private Boolean ativo;

    private Instant criadoEm;

    private Instant atualizadoEm;

    private Instant excluidoEm;
}
```

Utilize essa abordagem apenas para evitar repetição.

Não criar hierarquias adicionais ou abstrações complexas.

Apenas UMA classe base simples é suficiente.

```text

```

devem permanecer opcionais no banco.

```text
ativo = true
```

automaticamente ao criar um registro.

---

# 34. CONSTRAINTS

NÃO criar constraints `NOT NULL`, exceto:

```text
id
criado_em
```

Foreign Keys podem existir, porém devem aceitar NULL.

Também tenha cuidado com UNIQUE constraints.

Não crie uma constraint que impeça historização ou soft delete sem considerar registros inativos.

Por exemplo, para email de usuário, se futuramente for necessário UNIQUE, avaliar índice parcial:

```sql
WHERE ativo = true
```

em vez de impedir reutilização causada por registros excluídos logicamente.

# 38. JPA

Preferir relacionamentos:

```java
@ManyToOne(fetch = FetchType.LAZY)
@OneToOne(fetch = FetchType.LAZY)
@OneToMany(fetch = FetchType.LAZY)
```

quando apropriado.

Não utilizar `EAGER` indiscriminadamente.

Evitar relacionamentos bidirecionais quando não forem necessários.

Nunca retornar entidades JPA diretamente pelo controller.

---

# 39. DTOs

Criar DTOs separados das entidades.

Não colocar regras de obrigatoriedade nos DTOs ainda, exceto quando tecnicamente necessário para o identificador de uma operação específica.

Não utilizar:

```java
@NotBlank
@NotNull
```

em campos do domínio apenas por suposição.

A obrigatoriedade funcional será definida posteriormente a partir das telas e fluxos.

---

# 40. FLYWAY

Criar as migrations necessárias respeitando as migrations existentes.

Antes de criar uma migration nova:

1. verifique qual é a última versão existente;
2. utilize a próxima numeração disponível.

Não assumir automaticamente:

```text
V2
```

ou qualquer número.

Flyway deve ser a única fonte de criação/alteração do schema.

Não utilizar:

```text
ddl-auto=create
ddl-auto=update
```

Utilizar Hibernate somente para validação do schema.

---

# 42. NÃO IMPLEMENTAR AINDA

Não implementar nesta etapa:

* autenticação completa;
* JWT;
* integração com IA;
* RAG;
* algoritmo de escolha de coruja;
* regras definitivas de recompensa;
* algoritmo de choque do ovo;
* repetição espaçada avançada;
* ranking;
* moedas;
* fusão de corujas;
* marketplace;
* comunidade;
* notificações.

Criar apenas o modelo necessário para suportar essas funcionalidades futuramente.

1. criar entities;
2. criar enums;
3. configurar relacionamentos;
4. criar migrations;
5. criar Foreign Keys;
6. criar índices;

8. criar DTOs;
9. criar mappers;

12. compilar o projeto;
13. executar os testes;
14. executar as migrations no PostgreSQL;
15. iniciar Spring Boot;
16. garantir que Hibernate e Flyway estejam consistentes.

Corrigir todos os erros encontrados.

# 44. REGRA FINAL

As três regras mais importantes desta implementação são:

### 1.

TODAS as entidades possuem delete lógico.

Nenhuma exclusão normal deverá remover fisicamente registros do banco.

### 2.

Somente:

```text
id
criado_em
```

são obrigatórios no banco.

Todos os demais campos devem aceitar NULL.

### 3.

Criar a entidade:

```text
RECOMPENSA
```

para registrar explicitamente recompensas concedidas ao usuário e permitir seu vínculo com a `CORUJA`, além da sessão e ovo que eventualmente deram origem à recompensa.

Não altere essas três regras por considerar outro modelo mais convencional.
