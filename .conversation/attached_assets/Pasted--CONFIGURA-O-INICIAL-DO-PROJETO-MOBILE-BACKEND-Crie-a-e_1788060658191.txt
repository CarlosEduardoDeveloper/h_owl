# CONFIGURAÇÃO INICIAL DO PROJETO — MOBILE + BACKEND

Crie a estrutura inicial de um novo projeto composto por:

* aplicativo mobile em React Native;
* API backend em Spring Boot;
* banco de dados PostgreSQL.

Nesta etapa, NÃO implemente ainda as funcionalidades de negócio do aplicativo.

O objetivo deste primeiro trabalho é construir exclusivamente uma fundação técnica:

* simples;
* organizada;
* reutilizável;
* escalável;
* fácil de entender;
* preparada para crescimento gradual.

O projeto posteriormente receberá as telas e requisitos funcionais.

Não antecipe funcionalidades que ainda não foram solicitadas.

---

# 1. ESTRUTURA GERAL

Organize o workspace preferencialmente desta forma:

```text
/
├── mobile/
├── backend/
├── docker-compose.yml
├── .gitignore
└── README.md
```

Onde:

`mobile/`
contém exclusivamente o aplicativo React Native.

`backend/`
contém exclusivamente a API Spring Boot.

O PostgreSQL deve ser disponibilizado localmente através de Docker Compose.

Não utilizar arquitetura de microsserviços.

Neste momento teremos:

```text
React Native
      ↓
   REST API
      ↓
 Spring Boot
      ↓
 PostgreSQL
```

O backend será um monólito modular.

---

# 2. PRINCÍPIOS DE ARQUITETURA

Queremos uma arquitetura baseada em:

**MVC modularizado.**

A solução precisa permanecer simples.

Não utilizar:

* Clean Architecture excessivamente complexa;
* Hexagonal Architecture completa;
* CQRS;
* Event Sourcing;
* microsserviços;
* dezenas de abstrações sem necessidade;
* interfaces criadas apenas por formalidade;
* padrões complexos sem problema real para resolver.

Queremos um sistema pragmático.

Entretanto, também não queremos:

* controllers gigantes;
* regras de negócio dentro de controllers;
* acesso direto ao banco pelo controller;
* frontend com regras de negócio do backend;
* arquivos gigantes;
* componentes React Native monolíticos;
* código inteiro dividido apenas em pastas técnicas globais.

A estrutura deve permitir crescimento sem precisar reconstruir toda a aplicação posteriormente.

---

# 3. VERSÕES

Utilize somente versões GA/Stable.

Nunca utilize:

* alpha;
* beta;
* milestone;
* release candidate;
* nightly.

## Mobile

Utilizar a versão estável mais recente disponível de:

* React Native;
* TypeScript.

Se alguma biblioteca escolhida não for compatível com a versão atual do React Native, utilize a versão estável compatível mais recente.

Não faça downgrade de toda a aplicação apenas por conveniência sem necessidade.

## Backend

Utilizar a versão GA estável mais recente disponível de:

* Java compatível com a versão atual do Spring Boot;
* Spring Boot.

Não utilizar versões milestone ou release candidate do Spring.

## Banco

Utilizar uma versão estável e suportada do PostgreSQL.

# 5. BACKEND — MVC MODULARIZADO

Não organizar todo o projeto desta maneira:

```text
controller/
service/
repository/
entity/
dto/
```

com todas as funcionalidades misturadas dentro dessas pastas.

Queremos modularização por domínio/feature.

Estrutura conceitual:

```text
backend/src/main/java/.../

├── config/
├── shared/
└── modules/
    ├── exemplo/
    │   ├── controller/
    │   ├── service/
    │   ├── repository/
    │   ├── domain/
    │   ├── dto/
    │   └── mapper/
    │
    └── outroModulo/
        ├── controller/
        ├── service/
        ├── repository/
        ├── domain/
        ├── dto/
        └── mapper/
```

Não é necessário criar módulos fictícios apenas para preencher essa estrutura.

Inicialmente crie somente o necessário para comprovar a arquitetura.

A ideia é:

```text
Módulo
 ├── Controller
 ├── Service
 ├── Repository
 ├── Domain/Entity
 ├── DTO
 └── Mapper
```

# 6. RESPONSABILIDADES NO BACKEND

## Controller

Responsável somente por:

* receber requisições;
* validar inputs;
* chamar services;
* definir HTTP status;
* devolver DTOs.

Não colocar regra de negócio significativa no controller.

---

## Service

Responsável por:

* regras de negócio;
* orquestração;
* transações;
* comunicação com repositories;
* validações relacionadas ao domínio.

---

## Repository

Responsável por:

* persistência;
* consultas ao PostgreSQL.

Utilizar Spring Data JPA.

---

## Domain / Entity

Representa entidades do domínio e persistência.

Evite utilizar entidades JPA diretamente como contrato da API.

---

## DTO

Utilizar DTOs para comunicação externa da API.

Separar quando necessário:

```text
Input
Response
```

ou nomenclatura equivalente.

Evite criar DTOs diferentes quando eles forem absolutamente idênticos e não houver benefício prático.

---

## Mapper

Responsável por conversão entre:

```text
Entity ↔ DTO
```

Mantenha simples.

Não adicionar bibliotecas de mapping somente por conveniência nesta etapa.

Pode utilizar mapeamento manual inicialmente.

# 7. SHARED

A pasta `shared` deve conter SOMENTE elementos realmente compartilhados.

Exemplos futuros:

```text
shared/
├── exception/
├── response/
├── validation/
└── util/
```

Não transforme `shared` em uma pasta onde qualquer classe pode ser colocada.

Classes específicas de um módulo devem permanecer no próprio módulo.

# 8. TRATAMENTO GLOBAL DE EXCEÇÕES

Configurar tratamento global usando:

```java
@RestControllerAdvice
```

Criar estrutura simples para respostas de erro.

Exemplo conceitual:

```json
{
  "timestamp": "2026-08-30T12:00:00Z",
  "status": 400,
  "error": "Bad Request",
  "message": "Dados inválidos",
  "path": "/api/..."
}
```

Para erros de validação, retornar também os campos inválidos quando apropriado.

Não retornar stack trace para o cliente.

# 9. VALIDAÇÃO

Utilizar Bean Validation.

Exemplos futuros:

```java
@NotBlank
@NotNull
@Size
@Email
```

Validação estrutural deve ocorrer através dos DTOs de entrada.

Regras de negócio devem ser verificadas no Service.

# 10. BANCO POSTGRESQL

Configurar PostgreSQL como banco oficial.

Não utilizar H2 como banco principal.

Configurar através de variáveis de ambiente.

Exemplo:

```text
DB_HOST
DB_PORT
DB_NAME
DB_USERNAME
DB_PASSWORD
```

Nunca colocar senhas reais diretamente no código.

---

# 11. FLYWAY

Toda alteração estrutural do banco deverá ser controlada pelo Flyway.

Criar:

```text
src/main/resources/db/migration/
```

Utilizar padrão:

```text
V1__initial_structure.sql
V2__...
V3__...
```

Não utilizar:

```text
spring.jpa.hibernate.ddl-auto=create
```

ou:

```text
update
```

como mecanismo de criação do banco.

Hibernate deve apenas validar o schema quando apropriado.

Preferencialmente:

```text
ddl-auto=validate
```

após existir a migration necessária.

# 43. REGRA PARA ABSTRAÇÕES

Antes de criar:

* interface;
* abstract class;
* factory;
* adapter;
* facade;
* provider;
* manager;
* handler genérico;

pergunte se existe um problema real que essa abstração resolve.

Se não houver, não crie.

Exemplo:

Não precisamos de:

```text
IUserService
UserServiceImpl
```

apenas porque algumas arquiteturas Java utilizam esse padrão.

Se houver apenas uma implementação e nenhuma necessidade de contrato intercambiável:

```text
UserService
```

é suficiente.

Por outro lado, integrações externas que provavelmente terão implementações diferentes podem justificar interfaces futuramente.
